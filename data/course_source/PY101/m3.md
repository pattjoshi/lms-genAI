# Object-Oriented Python

Object-oriented programming (OOP) groups data and the functions that work on it into objects. Python supports OOP fully, and most libraries you will use, from Pandas to LangChain, are built from classes.

## Classes and Objects

Prerequisites: Functions, Dictionaries and Sets.

A class is a blueprint; an object is one instance built from it. You define a class with the `class` keyword. The special method `__init__` runs when a new object is created and sets its attributes, for example `self.name = name`.

The first parameter of every instance method is `self`, which refers to the object the method was called on. Python passes it automatically, so `riya.enroll("ML201")` is really `Student.enroll(riya, "ML201")`.

Attributes stored on `self` belong to one object, while attributes defined directly in the class body are shared by all instances. Methods whose names start and end with double underscores, called dunder methods, customise built-in behaviour: `__str__` controls how an object prints and `__eq__` controls how two objects compare with ==.

Encapsulation means hiding internal details behind methods. Python has no truly private attributes; by convention a leading underscore such as `_balance` means "internal, do not touch".

## Inheritance

Prerequisites: Classes and Objects.

Inheritance lets a class reuse and extend another class. In `class Teacher(User):` the Teacher class inherits every attribute and method of User and can add its own. User is called the parent or base class and Teacher the child or subclass.

A child class can override a parent method by defining a method with the same name. Inside the override, `super().method_name()` calls the parent's version so you can extend behaviour instead of replacing it completely. Calling `super().__init__()` in a child's constructor is the usual way to make sure the parent sets up its attributes.

Polymorphism means code can work with any subclass through the parent's interface: a function that accepts a User works for Students and Teachers alike.

Prefer composition (an object holding other objects) over deep inheritance trees. A useful test: inheritance should express an "is a" relationship, as in a Teacher is a User, while composition expresses "has a", as in a Course has Modules.

## Exceptions

Prerequisites: Control Flow, Classes and Objects.

An exception is an error that happens while a program runs, such as dividing by zero (ZeroDivisionError) or opening a missing file (FileNotFoundError). If nothing handles it, the program stops and prints a traceback.

You handle exceptions with `try` and `except`. Put the risky code in the try block and the recovery code in an except block that names the specific exception type. Catching every exception with a bare `except:` hides bugs and is considered bad practice.

The `else` block runs only if no exception occurred, and `finally` always runs, which makes it the right place for clean-up such as closing a connection. You raise your own exceptions with `raise ValueError("marks must be between 0 and 100")`.

Exceptions are classes, so you can define custom ones by inheriting from Exception, for example `class PaymentFailed(Exception): pass`. This is a practical use of inheritance.
